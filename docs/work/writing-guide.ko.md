# 대시보드에 보이는 글 쓰는 법 (에이전트 공통)

<!-- `lina work fields --markdown > docs/work/writing-guide.ko.md`로 만든다. 손으로 고치지 말고 hermes_cli/work/writing_fields.py를 고친다. -->

**읽는 사람은 주인이다.** 주인은 그 일의 맥락을 모르는 채로 요약 화면에서 처음 본다고 생각하고 쓴다. 일하면서 쓰던 말(파일, 명령, 기기, 이슈 번호, 내부 도구 이름)을 그대로 옮기지 않는다. 업무 도구(Linear, Jira, 노션 한국어판)의 할 일처럼 쓴다.

## 공통
- 쉬운 말로 쓴다. 한 칸에는 사실 하나만 쓴다.
- **넣지 않는 것:**
  - 이슈·PR 번호(`#19`)
  - 작업 번호(`OT-…`, `T…`, `G…`)
  - 기기 이름(`devices.workers`의 이름)
  - 명령과 옵션(`lina worker send`, `--omo`)
  - 파일·경로·커밋
  - 영어 코드 말(`breaker`, `verdict`)
  - 내부 도구 이름: `장부`는 쓰지 않는다. `작업판`은 `대시보드`로, `LCM`은 `기억 압축`으로, `omo`는 `작업`으로 쓴다.
- 제품·서비스 이름은 써도 된다. 예: GitHub, Claude, OpenAI, Gemini, Slack, Telegram, NAS.
- 괄호로 덧붙이지 않는다. 덧붙일 게 있으면 다른 칸에 쓴다.

## 칸별 규칙
| 칸 | 길이 | 모양 | 들어갈 것 |
|---|---|---|---|
| 목표 이름 | 25자 | 결과를 말하는 명사구 | 주인이 바라는 결과. 주인의 말에서 가져온다 |
| 완료 조건 | 60자 | 확인할 수 있는 상태 한 문장 | 무엇이 보이거나 되면 끝인지 |
| 할 일 제목 | 25자 | 대상 + 하는 일(…추가, …수정, …정리, …점검, …조사, …배포) | 이 할 일이 바꾸는 것 |
| 왜 | 40자 | 한 문장, `~게` 또는 `~려고`로 끝냄 | 이게 끝나면 주인에게 무엇이 좋아지나. 목표를 모르는 사람이 읽어도 알 수 있게 |
| 진행 메모 | 60자 | `~했다. 다음은 ~.` | 한 일과 다음 할 일 |
| 결정 문장 | 70자 | 질문은 `~할까?`, 요청은 `~해 줘` | 무엇을 정하거나 해야 하나 |
| 진행 대기 | 40자 | `정해지면 ~` | 정해지면 무엇이 움직이나 |
| 고를 답 | 15자 | 2~4개, 추천 하나 | 질문일 때만 |
| 대기 문장 | 50자 | `~를 기다림` | 무엇을, 누구를, 언제까지 |
| 멈춤 이유 | 50자 | 이유 + 풀리는 조건 | 누가 무엇을 하면 풀리나 |
| 답글 | 60자 | 한 일 + 확인한 것 | 결과 칩(반영함·반영 안 함·답변 필요)과 맞게 |
| 마감일 | 10자 | YYYY-MM-DD | 언제까지 끝내야 하나. 주인이나 요청에서 나온 날짜만 |

## 고쳐 쓴 예
| 전 | 제목 | 왜 |
|---|---|---|
| 주문 관문 #19: breaker 재확인·결과 비밀값 거르기 | 주문 관문 안전장치 점검 | 실주문을 켜도 승인 없이 주문이 나가지 않게 |
| LCM 수정 받아 전체 배포·전후 측정 | 기억 압축 수정 배포와 효과 측정 | 대화가 길어져도 답이 느려지지 않게 |
| 장부: 댓글·답글·완료 표시 | 대시보드 댓글과 완료 표시 | 대시보드에서 바로 의견을 남기고 끝을 표시하게 |
| lina worker send: 질문 대기 중 답 넣기 | 질문하며 멈춘 작업에 답 넣기 | 작업이 사람 답을 기다리며 멈춰 있지 않게 |
| OT-ABC 시험 작업 알림 확인 | 작업 완료 알림 점검 | 작업이 끝나면 맡은 에이전트에게 빠짐없이 알려지게 |
| 대시보드: 목표 함께 완료 묻기 상자 다듬기 | 목표 완료 확인 창 다듬기 | 열린 할 일이 남은 목표를 실수로 닫지 않게 |

## 검사
`work`는 글을 쓰기 전에 칸마다 아래 규칙을 본다. 거절하면 아무것도 쓰지 않는다. `work lint`는 이미 쓴 글 가운데 어긋난 것을 보여 주고, `work fields`는 칸마다 설명과 예를 보여 준다.

| 거절 규칙 | 걸리는 글(정규식, 영문 단어 경계) |
|---|---|
| 이슈·PR 번호 | `#\d+` |
| 작업 번호 | `\b(?:OT\|OG\|OS)-[A-Z0-9]+\|\b[TG]\d{2,}\b` |
| 명령과 옵션 | `\blina (?:worker\|work)\b\| --[a-z]` |
| 경로 | `/Users/\|/home/\|~/` |
| 내부 이름 | `장부\|작업판\|\bomo\b\|\bLCM\b` |
| 괄호 | `[()]` |
| 앞머리 꼬리표 | `^[^\s:]+:\s` (목표 이름·할 일 제목) |
| 길이 | 칸별 규칙 표의 길이를 넘는 글 |

경고만 하는 것: 영어 단어가 셋 이상 이어질 때, 허용 목록 밖 영어 단어가 있을 때. 허용 목록: GitHub, Claude, OpenAI, Gemini, Slack, Telegram, NAS, Codex, Grok, Cursor, Antigravity, OCX, Synology, iPhone, Mac.

| 칸 | 쓰는 곳 | 꼭 쓰나 | 걸리면 | 쓰는 명령 |
|---|---|---|---|---|
| 목표 이름 | 목표 | 꼭 | 거절 | work add 목표 --title · work edit --title |
| 완료 조건 | 목표·할 일 | 꼭 | 경고 | work add --done · work edit --done |
| 할 일 제목 | 할 일 | 꼭 | 거절 | work add 할 일 --title · work edit --title |
| 왜 | 할 일 | 꼭 | 거절 | work add 할 일 --why · work edit --why |
| 진행 메모 | 메모 | 선택 | 경고 | work note · work add --note |
| 결정 문장 | 결정 | 선택 | 거절 | work wait --decide · work edit --decide |
| 진행 대기 | 결정 | 선택 | 거절 | 대시보드가 쓴다 · work plain |
| 고를 답 | 결정 | 선택 | 거절 | work wait --choice |
| 대기 문장 | 대기 | 기다릴 때 꼭 | 거절 | work wait --on --next |
| 멈춤 이유 | 대기 | 선택 | 거절 | work wait --hold --on |
| 답글 | 답글 | 선택 | 경고 | work reply |
| 마감일 | 목표·할 일 | 선택 | 거절 | work add --due · work edit --due |

## 칸마다 예

### 목표 이름
예 출처: 가이드

- 좋은 예: 대시보드 댓글과 완료 표시
- 좋은 예: 기억 압축 수정 배포와 효과 측정
- 나쁜 예: 장부: 댓글·답글·완료 표시 — 내부 이름, 앞머리 꼬리표
- 나쁜 예: LCM 수정 받아 전체 배포·전후 측정 — 내부 이름, 허용 목록 밖 영어 단어

### 완료 조건
예 출처: 지어냄

- 좋은 예: 실주문을 켜도 승인 없는 주문이 하나도 나가지 않는다
- 좋은 예: 대시보드에서 댓글을 달면 맡은 에이전트에게 알림이 간다
- 나쁜 예: breaker verdict 재확인 완료 — 허용 목록 밖 영어 단어
- 나쁜 예: #19 닫힘 — 이슈·PR 번호

### 할 일 제목
예 출처: 가이드

- 좋은 예: 주문 관문 안전장치 점검
- 좋은 예: 작업 완료 알림 점검
- 나쁜 예: 주문 관문 #19: breaker 재확인·결과 비밀값 거르기 — 길이 25자 넘음, 이슈·PR 번호, 허용 목록 밖 영어 단어
- 나쁜 예: OT-ABC 시험 작업 알림 확인 — 작업 번호, 허용 목록 밖 영어 단어

### 왜
예 출처: 가이드(좋은 예) · 지어냄(나쁜 예)

- 좋은 예: 실주문을 켜도 승인 없이 주문이 나가지 않게
- 좋은 예: 작업이 끝나면 맡은 에이전트에게 빠짐없이 알려지게
- 나쁜 예: 실주문 전에 breaker 재확인하려고 (#19) — 이슈·PR 번호, 괄호, 허용 목록 밖 영어 단어
- 나쁜 예: omo 알림이 제대로 오게 — 내부 이름, 허용 목록 밖 영어 단어

### 진행 메모
예 출처: 지어냄

- 좋은 예: 안전장치 시험을 돌렸다. 다음은 실주문 설정 점검.
- 좋은 예: 알림 누락 두 건을 고쳤다. 다음은 하루 지켜보기.
- 나쁜 예: lina worker send 돌림 — 명령과 옵션, 영어 단어 셋 이상 이어짐, 허용 목록 밖 영어 단어
- 나쁜 예: PR #19 머지함 (CI green) — 이슈·PR 번호, 괄호, 허용 목록 밖 영어 단어

### 결정 문장
예 출처: 지어냄

- 좋은 예: 실주문 안전장치 기준을 지금대로 둘까?
- 좋은 예: 증권 앱에서 주문 승인을 한 번 눌러 줘
- 나쁜 예: breaker 기준 (3회) 유지? — 괄호, 허용 목록 밖 영어 단어
- 나쁜 예: OT-ABC1101 결과 보고 --omo 켤까? — 작업 번호, 명령과 옵션, 내부 이름, 허용 목록 밖 영어 단어

### 진행 대기
예 출처: 지어냄

- 좋은 예: 정해지면 실주문 설정을 바꾼다
- 좋은 예: 정해지면 남은 할 일을 닫는다
- 나쁜 예: 정해지면 ~/bin에서 재시작 (수동) — 경로, 괄호, 허용 목록 밖 영어 단어
- 나쁜 예: 정해지면 #21 진행 — 이슈·PR 번호

### 고를 답
예 출처: 지어냄

- 좋은 예: 지금대로 두기
- 좋은 예: 다음 주로 미루기
- 나쁜 예: 유지 (추천) — 괄호
- 나쁜 예: OT-ABC 보고 나서 정하기 — 길이 15자 넘음, 작업 번호, 허용 목록 밖 영어 단어

### 대기 문장
예 출처: 지어냄

- 좋은 예: 빌드 기기 재부팅을 오늘 밤까지 기다림
- 좋은 예: 인증 메일을 금요일까지 기다림
- 나쁜 예: lina worker 재부팅 기다림 — 명령과 옵션, 허용 목록 밖 영어 단어
- 나쁜 예: ~/Desk 동기화 기다림 — 경로, 허용 목록 밖 영어 단어

### 멈춤 이유
예 출처: 지어냄

- 좋은 예: 주문 한도가 없어 멈춤. 주인이 한도를 정하면 풀림
- 좋은 예: NAS가 꺼져 멈춤. NAS가 켜지면 풀림
- 나쁜 예: /home 디스크 다운 — 허용 목록 밖 영어 단어
- 나쁜 예: LCM 오류 (원인 모름) — 내부 이름, 괄호, 허용 목록 밖 영어 단어

### 답글
예 출처: 지어냄

- 좋은 예: 알림 문구를 고쳤다. 시험 알림이 에이전트에게 간 것을 봤다.
- 좋은 예: 말씀대로 미뤘다. 다음 주 월요일에 다시 묻겠다.
- 나쁜 예: fixed in PR #19 — 이슈·PR 번호, 영어 단어 셋 이상 이어짐, 허용 목록 밖 영어 단어
- 나쁜 예: 작업판 수정 (abc123 커밋) — 내부 이름, 괄호, 허용 목록 밖 영어 단어

### 마감일
예 출처: 지어냄

- 좋은 예: 2026-11-05
- 좋은 예: 2026-11-30
- 나쁜 예: 11-05 — 날짜 모양
- 나쁜 예: 다음 주 금요일 — 날짜 모양
